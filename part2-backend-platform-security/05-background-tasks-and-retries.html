Background Jobs, Idempotency, and Retries in FastAPI

The concurrency chapter kept independent HTTP requests from blocking one another. This chapter handles a different problem: work that should outlive the request itself. We will move document ingestion into a job, make job creation safe to retry, retry only transient downstream failures, and preserve tenant identity from submission through completion.

The target interaction POST /ingest accepts work quickly and returns 202 Accepted with a job_id. A worker performs the expensive extraction, embedding, and indexing. The client polls GET /jobs/{job_id} or receives a notification later.

1) Why slow work should not run inside the request

A normal HTTP request has a limited time budget. A reverse proxy, load balancer, browser, or mobile client may time out even though the server is still extracting a document. If the client retries, the server may start the same expensive operation twice.

Document ingestion is a good running example because it usually contains several independently fallible steps:

  1. Persist the upload or object reference.
  2. Extract and normalize text.
  3. Split text into chunks.
  4. Call an embedding service.
  5. Write vectors and metadata to an index.
  6. Mark the document ready for retrieval.

The request should record the intent to perform those steps, not remain open until every step finishes.

2) Separate best-effort background callbacks from durable jobs

FastAPI's BackgroundTasks schedules a callable after the response is sent. It is useful for short, non-critical work such as a small audit write or cache cleanup when losing that work is acceptable.

It is not a durable queue. The callback runs in the application process. A restart, deployment, crash, autoscaling event, or process termination can lose the task. Long callbacks also consume the same application's resources.

Work typeAppropriate mechanismReason
Short, best-effort action after a responseFastAPI BackgroundTasksSimple and local; loss is acceptable.
Document ingestion, email delivery, webhook, media processingDurable queue plus workerSurvives restarts and supports retries, visibility, and dead-letter handling.
Multi-step workflow with waits or compensationWorkflow engine or orchestratorPersists step state and long-running control flow.
Periodic workScheduler that enqueues a durable jobSeparates schedule ownership from execution.

Cloud Tasks, Pub/Sub with a subscriber, Celery or RQ with a durable broker, and managed workflow services are common choices. The exact product matters less than the guarantees you require: persistence, delivery semantics, retry policy, visibility timeout or lease, concurrency control, and a dead-letter path.

3) First implementation: see the complete interaction with BackgroundTasks

The following in-memory version is deliberately small. It demonstrates the HTTP contract, idempotency key, identity propagation, and state transitions. The production section immediately afterward replaces its unsafe storage assumptions.

from threading import Lock
from typing import Annotated, Literal
from uuid import uuid4
import time

from fastapi import BackgroundTasks, Depends, FastAPI, Header, HTTPException, status
from pydantic import BaseModel, Field

app = FastAPI()

class Identity(BaseModel):
    tenant_id: str
    user_id: str

def get_identity() -> Identity:
    # Teaching stand-in. Production verifies a bearer token and maps claims.
    return Identity(tenant_id="tenant-acme", user_id="user-123")

class IngestRequest(BaseModel):
    document_uri: str

class IngestResponse(BaseModel):
    job_id: str
    status: Literal["queued"]

class JobView(BaseModel):
    job_id: str
    document_uri: str
    status: Literal["queued", "running", "succeeded", "failed"]
    error: str | None = None

# Teaching-only process memory. Production uses a database + durable queue.
JOBS: dict[str, dict] = {}
IDEMPOTENCY: dict[tuple[str, str], IngestResponse] = {}
STORE_LOCK = Lock()

def ingest_job(job_id: str) -> None:
    try:
        JOBS[job_id]["status"] = "running"
        time.sleep(2)  # stand-in for extract -> embed -> index
        JOBS[job_id]["status"] = "succeeded"
    except Exception as exc:
        JOBS[job_id]["status"] = "failed"
        JOBS[job_id]["error"] = str(exc)

@app.post(
    "/ingest",
    response_model=IngestResponse,
    status_code=status.HTTP_202_ACCEPTED,
)
def ingest(
    payload: IngestRequest,
    background: BackgroundTasks,
    identity: Annotated[Identity, Depends(get_identity)],
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
) -> IngestResponse:
    store_key = (identity.tenant_id, idempotency_key)

    # The lock makes the teaching store's check-and-create atomic in one process.
    with STORE_LOCK:
        if previous := IDEMPOTENCY.get(store_key):
            return previous

        job_id = str(uuid4())
        response = IngestResponse(job_id=job_id, status="queued")

        JOBS[job_id] = {
            "job_id": job_id,
            "tenant_id": identity.tenant_id,
            "user_id": identity.user_id,
            "document_uri": payload.document_uri,
            "status": "queued",
            "error": None,
        }
        IDEMPOTENCY[store_key] = response

    background.add_task(ingest_job, job_id)
    return response

The client supplies the same idempotency key every time it retries the same logical submission:

Idempotency-Key: 9c2f9f2f-9bd8-4d1e-8b45-4a338f89f9a0
Content-Type: application/json

{"document_uri": "gs://tenant-acme/inbox/report.pdf"}

Concurrency detail: “look up the key, then insert” must be one atomic operation. A Python dictionary and lock only protect one teaching process. In production, enforce a database unique constraint on a key such as (tenant_id, operation, idempotency_key) and commit the idempotency record with the job record in one transaction.

4) Return job state without crossing tenant boundaries

A job_id is an identifier, not authorization. Every status read, cancel operation, artifact download, and retry must check the tenant from the verified request identity against the tenant stored on the job.

@app.get("/jobs/{job_id}", response_model=JobView)
def get_job(
    job_id: str,
    identity: Annotated[Identity, Depends(get_identity)],
) -> JobView:
    job = JOBS.get(job_id)

    # Returning 404 for both cases avoids revealing another tenant's job IDs.
    if job is None or job["tenant_id"] != identity.tenant_id:
        raise HTTPException(status_code=404, detail="Job not found")

    return JobView.model_validate(job)

For user-owned jobs, add a user_id check too. For shared tenant jobs, authorize by role or permission. The worker must also scope every database read, object-store path, vector-index namespace, and emitted event using the job's persisted tenant context.

5) Idempotency means one logical effect, not merely one HTTP response

An idempotency record should normally retain:

  • tenant or principal scope;
  • operation name and idempotency key;
  • a hash of the normalized request payload;
  • the created resource or job ID;
  • the original status code and response body;
  • creation time, expiry policy, and processing state.

If the same key arrives with a different payload hash, reject it with a conflict rather than silently returning an unrelated response. Keep the retention period at least as long as the maximum client retry window.

Delivery semantics Most practical queues are at least once: a worker may receive the same message more than once. “Exactly once” business behavior is therefore built from idempotent consumers, unique constraints, conditional writes, and deduplication, not from assuming the queue will never redeliver.

6) Retry only failures that can plausibly succeed later

Retries help transient faults such as timeouts, connection resets, rate limits, and temporary service unavailability. They make permanent faults worse by adding latency and load.

FailureRetry?Typical handling
Timeout, connection reset, HTTP 502/503/504UsuallyBounded exponential backoff with jitter.
HTTP 429UsuallyRespect Retry-After; apply rate limiting.
HTTP 401Only after credential refreshRefresh once; repeated 401 is permanent for this attempt.
HTTP 403NoFix authorization or policy.
HTTP 400/422 or schema validation errorNoCorrect the request or quarantine the message.
Not foundContext dependentRetry only when eventual consistency is expected and bounded.

A small retry helper with exponential backoff and jitter

from collections.abc import Callable
from random import uniform
from time import sleep
from typing import TypeVar

T = TypeVar("T")

class TransientError(Exception):
    pass

def retry_transient(
    operation: Callable[[], T],
    *,
    attempts: int = 4,
    base_delay: float = 0.25,
    max_delay: float = 4.0,
) -> T:
    last_error: TransientError | None = None

    for attempt in range(attempts):
        try:
            return operation()
        except TransientError as exc:
            last_error = exc
            if attempt == attempts - 1:
                break

            cap = min(max_delay, base_delay * (2 ** attempt))
            sleep(uniform(0, cap))  # full jitter prevents synchronized retries

    assert last_error is not None
    raise last_error

A production HTTP client library or queue normally provides retry hooks. Use those rather than maintaining a general retry framework yourself, but keep the same policy questions explicit: which exceptions, how many attempts, what deadline, whether the operation is idempotent, and how Retry-After is handled.

7) Retry steps, not an opaque whole workflow

The original ingestion example called two flaky dependencies. Keep those steps independently observable and idempotent:

def call_search_index(job: dict) -> None:
    # Use a deterministic document ID so a retry overwrites/upserts,
    # rather than creating duplicate indexed documents.
    ...

def call_embedding_service(job: dict) -> list[list[float]]:
    # A pure request is safe to repeat; cache by content hash when useful.
    ...

def run_ingestion(job_id: str) -> None:
    job = load_job(job_id)
    mark_running(job_id)

    try:
        vectors = retry_transient(lambda: call_embedding_service(job))
        retry_transient(lambda: call_search_index({**job, "vectors": vectors}))
        mark_succeeded(job_id)
    except TransientError as exc:
        mark_failed(job_id, code="retries_exhausted", detail=str(exc))
        raise

Checkpointing matters for expensive workflows. If extraction succeeded but indexing failed, a retry should resume at indexing when possible rather than repeat the upload and extraction. Store step state and immutable input references so a worker can reconstruct the attempt.

8) Durable production pattern: transaction, queue, worker

The central reliability problem is a dual write: what if the API commits the job row but crashes before publishing to the queue, or publishes to the queue but fails before committing the job row?

The transactional outbox pattern solves this when the job database and broker cannot share one transaction:

  1. In one database transaction, insert the job, idempotency record, and an outbox event.
  2. Commit once.
  3. A relay publishes unsent outbox rows to the queue.
  4. After publish succeeds, mark the outbox row sent.
  5. The worker consumes idempotently because relay or broker delivery can repeat.
API transaction
  ├─ jobs(job_id, tenant_id, status="queued", ...)
  ├─ idempotency(tenant_id, key, request_hash, job_id, ...)
  └─ outbox(event_id, type="ingest.requested", payload, sent_at=NULL)

Outbox relay → durable queue → worker → status/artifacts

Some managed task queues let the API create the task directly with a deterministic task name and provide adequate deduplication for your use case. Document the chosen guarantee rather than assuming every queue behaves the same.

9) Failure, cancellation, and dead-letter handling

A job state machine should make terminal and non-terminal states explicit. A practical minimum is queued, running, succeeded, failed, and canceled. Add retry_scheduled or step-level states only when operators need them.

  • After retries are exhausted, move or route the message to a dead-letter queue and mark the job failed with a stable error code.
  • Make cancellation cooperative: set cancel_requested and let workers stop between safe steps.
  • Do not expose internal stack traces to clients; preserve them in restricted logs.
  • Define whether operators can replay a failed job and whether replay creates a new attempt or a new job.
  • Use a lease or visibility timeout so abandoned work can be redelivered after a worker crash.

10) Observability and operational controls

Every log, metric, and trace should carry job_id, tenant_id, attempt number, step name, and correlation or trace ID. Useful metrics include queue age, processing duration, retry count, success rate, dead-letter volume, and jobs stuck in a non-terminal state.

What to remember

  • BackgroundTasks is for short best-effort callbacks, not durable ingestion.
  • Return 202 Accepted and a job resource when work continues after the request.
  • Make the idempotency check and job creation atomic and tenant-scoped.
  • Assume at-least-once delivery and make workers and side effects idempotent.
  • Retry transient failures with bounded backoff and jitter; do not retry validation or authorization failures.
  • Persist tenant and user context on the job and re-authorize every status or artifact read.
  • Use an outbox or equivalent mechanism when database state and queue publication must agree.
