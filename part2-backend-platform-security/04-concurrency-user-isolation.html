FastAPI Concurrency and Per-Request User Isolation

6 min read·8 sections
On this page

How one service keeps many in-flight requests efficient without mixing user or tenant state.

Where this fits The preceding chapter established typed request boundaries with Pydantic. This chapter follows several validated requests while they execute at the same time. The next chapter moves slow work into durable background jobs without losing the same identity and tenant context.

1. What happens when 1000 users hit your API

When thousands of users call your FastAPI endpoint simultaneously, Uvicorn (the ASGI server) accepts the connections. Within each worker process, the ASGI application handles each active request in its own in-flight task and request scope.

For every single request, FastAPI:

  • Matches the method + path (e.g., POST /query) to the correct function.
  • Parses headers, query parameters, and the body specific to that request.
  • Calls your function with fresh arguments.
Key Concept: Each user request triggers an independent function call.

Function arguments and local variables belong to that invocation. They are safe to interleave because Request A does not reuse Request B's Python stack frame. This is request isolation, not authorization: your code must still verify the caller and scope every data operation.

2. Why async lets one server handle lots of traffic

Most API operations are I/O-bound: waiting for database queries, Elasticsearch results, or external APIs (like Azure OpenAI).

If your endpoint is defined with async def and uses await for I/O, the event loop can pause a waiting request (Request A) and process others (Request B, C) in the meantime. This allows a single process to handle thousands of concurrent connections efficiently.

@app.post("/query")
async def query():
    chunks = await es_search(...)       # waiting -> event loop runs other requests
    answer = await call_openai(...)     # waiting -> event loop runs other requests
    return {"answer": answer}
Important: If you use blocking code (like time.sleep() or a synchronous HTTP client) inside async def, you freeze the event loop and kill concurrency.

async def helps only when the libraries underneath it are asynchronous and the function reaches an await. A synchronous FastAPI endpoint is normally run in a thread pool, which is useful for blocking libraries but has finite capacity. CPU-heavy inference, image processing, and large dataframe work should use a separate process, worker service, or batch platform rather than occupying the API event loop.

3. Concurrency vs. Parallelism

It is important to distinguish between these two scaling mechanisms:

A) Async Concurrency

(Recommended for I/O)

  • One process + one event loop.
  • Thousands of “tasks” can be in flight.
  • Best when you await I/O operations.

B) Parallelism (Workers)

(Multi-process)

  • Run multiple Uvicorn worker processes.
  • Each process has its own event loop.
  • Utilizes multiple CPU cores.

Production systems usually combine both mechanisms: asynchronous I/O inside each worker, several workers or container replicas for CPU capacity and resilience, and a load balancer in front. Worker count is not a substitute for sizing database and HTTP connection pools; every replica can multiply downstream connections.

4. How FastAPI keeps users separate (Per-Request Identity)

FastAPI does not “assign a user to a thread.” Instead, every HTTP request is isolated. User identity is derived from the request itself (usually via a JWT in the Authorization header), and your code uses this identity to scope data access.

Concrete Example

Two users hit the same endpoint at the same time, but get different results.

from typing import Annotated

from fastapi import Depends, FastAPI, Header, HTTPException, status
from pydantic import BaseModel

app = FastAPI()

class QueryReq(BaseModel):
    question: str

class Identity(BaseModel):
    tenant_id: str
    user_id: str

# Dependency to extract identity from a verified bearer token
def get_identity(
    authorization: Annotated[str | None, Header()] = None,
) -> Identity:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Missing bearer token",
        )

    token = authorization.removeprefix("Bearer ").strip()

    # Verify signature, issuer, audience, expiry, and required claims.
    claims = verify_and_decode_jwt(token)
    return Identity(tenant_id=claims["tenant_id"], user_id=claims["sub"])

@app.post("/query")
async def query(
    req: QueryReq,
    ident: Annotated[Identity, Depends(get_identity)],
):
    # The repository requires tenant_id; callers cannot "forget" the filter.
    chunks = await search_repository.search(
        tenant_id=ident.tenant_id,
        question=req.question,
    )
    return {"user_id": ident.user_id, "chunks": chunks}

User A Request

Authorization: Bearer <verified JWT for Alice>

FastAPI calls:

ident=Identity(tenant_id="tenant-1", ...)

User B Request

Authorization: Bearer <verified JWT for Bob>

FastAPI calls:

ident=Identity(tenant_id="tenant-2", ...)

Same code, same route — but different identity → tenants stay isolated.

5. Critical Rule: No Global State

Never use global variables for per-user state. Globals are shared across all requests in a process.



CURRENT_USER = None # unsafe: shared across requests in this process

Instead, keep per-user/per-request data in:

  • Function local variables (ident, req)
  • Dependencies (Depends(get_identity))
  • request.state (middleware context)

Module-level objects are not automatically wrong. Immutable configuration, database pool objects, HTTP clients, and model clients are normally shared. The unsafe pattern is putting mutable request data such as current_user, tenant_id, or a partially built response in them.

6. Tenant isolation must survive every boundary

A verified identity is only the starting point. Carry the derived tenant and user identifiers through every call that can read, cache, enqueue, or store data.

BoundaryIsolation ruleTypical backstop
Repository / SQLRequire tenant_id in the method signature and query predicate.Row-level security and composite constraints.
Search indexAdd a non-optional tenant filter to every query.Separate index/namespace for higher-risk tenants.
CacheInclude tenant and authorization-relevant version data in the key.Short TTL and explicit invalidation.
Object storageDerive the allowed prefix from trusted request context, never from an unchecked body field.Separate buckets or policy conditions where appropriate.
Background jobPersist tenant, initiating user, authorization snapshot/version, and job ID.Worker-side re-authorization for sensitive effects.

7. Backpressure is part of concurrency design

Accepting more concurrent requests than downstream systems can serve creates a queue inside your application. Latency rises, retries multiply the load, and eventually everything times out. Bound concurrency deliberately:

  • Set connection-pool limits for databases and outbound HTTP clients.
  • Use explicit connect, read, write, and pool-acquisition timeouts.
  • Use a semaphore or worker queue around scarce downstream capacity.
  • Return 429 Too Many Requests for caller-specific rate limits and 503 Service Unavailable when shared capacity is temporarily exhausted.
  • Retry only transient failures, with exponential backoff and jitter; Chapter 6 develops that policy.

8. Cancellation, disconnects, and observability

A client can disconnect while work is still running. Cooperative asynchronous libraries can receive cancellation, but an external side effect may already have happened. Use idempotency keys for effects, keep request deadlines shorter than infrastructure deadlines, and move work that must finish after disconnect into a durable job.

Logs and traces should include a request ID, tenant ID, subject or internal user ID, route, downstream dependency, and latency. Do not log bearer tokens, raw secrets, or unnecessary personal data. A load test is incomplete unless it also checks cross-tenant leakage and downstream pool saturation.

Operational test Run Alice and Bob requests concurrently, deliberately delay one downstream call, and assert that each response, cache key, SQL query, trace, and queued message retains the correct tenant.
