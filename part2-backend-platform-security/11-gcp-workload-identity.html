GCP Project Setup and Workload Identity

Project Setup

Begin by organizing your Google Cloud resources under a single Organization (especially if you have Google Workspace). Under the organization, use Folders and Projects to separate concerns. A common approach is one project per environment (e.g. myapp-dev, myapp-prod). This isolates IAM boundaries and billing by environment. For example:

  • Create a project for production and one for development: 
    gcloud projects create myapp-prod --name="MyApp Production" --organization=ORG_ID 
gcloud projects create myapp-dev  --name="MyApp Development" --organization=ORG_ID
  • Link each project to a billing account: 
    gcloud billing projects link myapp-prod --billing-account=BILLING_ACCOUNT_ID  
gcloud billing projects link myapp-dev  --billing-account=BILLING_ACCOUNT_ID
    (You can list billing accounts via gcloud billing accounts list.)
  • Optionally, use Folders to group projects (e.g. Network, Platform, Services folders). Folders allow applying policies to multiple projects, and projects segregate environments and teams.

A project can contain one or more VPC networks. Google Cloud may create a default network for a new standalone project, unless an organization policy suppresses it, but production platforms should create and manage their network topology explicitly. You can use separate custom VPCs per project or a centrally governed Shared VPC host project. For example, create a custom VPC in the prod project:

gcloud compute networks create my-vpc --project=myapp-prod --subnet-mode=custom
gcloud compute networks subnets create subnet-us --project=myapp-prod \
    --network=my-vpc --region=us-central1 --range=10.10.0.0/16

If using Shared VPC, set up one “host” project containing the VPC, and attach service projects (e.g. myapp-prod) to it. Configure firewall rules to allow only necessary traffic (for example, allow public HTTPS only to the external load balancer, allow Google health-check ranges to backend services, and keep database traffic private). These are separate controls: Private Google Access lets resources without external IP addresses reach supported Google APIs, while Cloud SQL private IP requires private services access or the currently supported Private Service Connect design. Enabling one does not configure the other.

Finally, tag and label your projects and resources for clarity (e.g. env=prod). At the org level, enforce policies (such as disabling default-credential grants) so that service accounts must have only the permissions you grant.

IAM and Service Accounts

Use IAM roles and service accounts with least privilege. For each project, create Google service accounts (GSAs) for the workloads and grant them only needed roles. For example:

  • Cloud Run frontend: Create a service account (e.g. frontend-sa@myapp-prod.iam.gserviceaccount.com) and give it only the roles needed (e.g. roles/storage.objectViewer if it reads from Cloud Storage, or other roles for backend calls). Assign this SA to the Cloud Run service with --service-account=frontend-sa@.... Avoid using the default Compute Engine SA broadly; instead use user-managed SAs with minimal permissions.
  • GKE backend: Create a Google SA (e.g. backend-sa@myapp-prod.iam.gserviceaccount.com) for the FastAPI pods. Grant it roles like roles/cloudsql.client (to access Cloud SQL) and roles/logging.logWriter. For example: 
    gcloud iam service-accounts create backend-sa --display-name="Backend Service Account"
gcloud projects add-iam-policy-binding myapp-prod \
    --member="serviceAccount:backend-sa@myapp-prod.iam.gserviceaccount.com" \
    --role="roles/cloudsql.client"

gcloud projects add-iam-policy-binding myapp-prod \
    --member="serviceAccount:backend-sa@myapp-prod.iam.gserviceaccount.com" \
    --role="roles/logging.logWriter"
  • Workload Identity Federation for GKE: Enable it so pods can obtain short-lived Google credentials without service-account key files. When creating the GKE cluster, use --workload-pool=PROJECT_ID.svc.id.goog. GKE creates the workload identity pool PROJECT_ID.svc.id.goog for the project. Then choose one of two authorization patterns:
    1. Direct resource access, preferred when the target API supports federated principals: grant the Kubernetes workload principal the required role directly on the resource or project.
    2. IAM service-account impersonation, for compatibility: allow a Kubernetes ServiceAccount (KSA) to impersonate a Google service account (GSA), then annotate the KSA with that GSA.
    A direct grant for default/backend-ksa looks like this: 
    PROJECT_ID=myapp-prod
PROJECT_NUMBER="$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')"

gcloud projects add-iam-policy-binding "$PROJECT_ID" \
  --role="roles/logging.logWriter" \
  --member="principal://iam.googleapis.com/projects/${PROJECT_NUMBER}/locations/global/workloadIdentityPools/${PROJECT_ID}.svc.id.goog/subject/ns/default/sa/backend-ksa"
    If a service requires GSA impersonation, the IAM binding and KSA annotation are both required: 
    gcloud iam service-accounts add-iam-policy-binding \
  backend-sa@myapp-prod.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="serviceAccount:myapp-prod.svc.id.goog[default/backend-ksa]"
    apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-ksa
  namespace: default
  annotations:
    iam.gke.io/gcp-service-account: backend-sa@myapp-prod.iam.gserviceaccount.com
    Then deploy the KSA and set serviceAccountName: backend-ksa on the Pod. The annotation alone is not an authorization grant: the roles/iam.workloadIdentityUser binding above is what permits impersonation. Google client libraries use Application Default Credentials (ADC), and the GKE metadata server exchanges the KSA token for short-lived credentials.
  • Cloud Run authentication to GCP: Cloud Run uses its service identity (the Google SA you assign) to call other Google Cloud services. By default Cloud Run will fetch tokens from its metadata server and use ADC. Ensure the Cloud Run SA has the right roles (for example roles/storage.objectViewer to read static objects, roles/storage.objectUser to write objects, and roles/iam.serviceAccountTokenCreator only if it truly needs to mint tokens). As above, use a user-managed SA and avoid broad roles like Editor or project-wide Storage Admin unless there is a specific operational reason.

Remember to use Google Groups to manage user access to projects. Assign IAM roles to groups (e.g. “NetworkAdmin”, “DevOps”, “AppDeveloper”) rather than individual users.

Authentication with Google Identity (OIDC)

To authenticate end-users, use Google’s OAuth2/OpenID Connect. First, create OAuth 2.0 credentials in your project: in the Cloud Console go to APIs & Services > Credentials > Create > OAuth Client ID. Choose “Web application” and set your React app’s origin and redirect URI (e.g. https://myapp.example.com and https://myapp.example.com/oauth2callback). This gives you a Client ID.

In your React frontend, use Google Identity Services or another maintained OAuth/OIDC library to implement the authorization code flow with PKCE. The authorization endpoint returns a short-lived authorization code; the client or a backend-for-frontend exchanges that code at the token endpoint. With scope=openid email profile, the token response can include an ID token that describes the authenticated user. For higher-sensitivity applications, a backend-for-frontend can perform the exchange and establish an HttpOnly, Secure, SameSite session cookie so browser JavaScript does not retain long-lived tokens.

An ID token is evidence of authentication for the OAuth client; it is not a general-purpose access token for arbitrary APIs. Validate it at the login/session boundary, then establish your own application session. If your API directly accepts Google-issued access tokens, validate their intended audience and scopes using the resource-server rules for that API. The following ID-token check is appropriate at a sign-in endpoint:

from google.oauth2 import id_token
from google.auth.transport import requests

try:
    # TOKEN is the ID token string from the client, and CLIENT_ID is your OAuth 2.0 client ID
    id_info = id_token.verify_oauth2_token(TOKEN, requests.Request(), CLIENT_ID)
    # The token is valid. You can trust id_info['sub'], id_info['email'], etc.
except ValueError:
    # Invalid token
    raise Unauthorized()

The verify_oauth2_token call checks the token’s signature, issuer (https://accounts.google.com or Google’s equivalent issuer form), audience, and lifetime. If valid, id_info contains the user’s Google identity. Use the stable sub claim as the external identity key; treat email as mutable display/contact data, and enforce hosted-domain policy explicitly if your application requires it. The backend can then create its own session without handling the user’s Google password.

Key points: Local ID-token verification does not require the obsolete Google+ API. Configure the OAuth consent screen and the correct web OAuth client, use that client ID as the expected audience, register exact origins and redirect URIs, and use maintained Google Identity/OAuth libraries rather than writing the protocol by hand.

Data Storage Design

For application data, choose managed GCP services:

  • Relational data (Cloud SQL for PostgreSQL): Cloud SQL is a fully managed PostgreSQL database (with high availability, automated backups, patching). Create a Cloud SQL instance in your project: 
    gcloud sql instances create my-postgres --database-version=POSTGRES_15 \
    --tier=db-f1-micro --region=us-central1 --network=my-vpc
gcloud sql databases create mydb --instance=my-postgres
    Grant the workload principal or impersonated GSA the Cloud SQL Client role so it can open an authorized connection through the Cloud SQL Auth Proxy or a connector. On GKE, you can also use private IP after configuring the required private network connection. Keep the layers separate: Workload Identity supplies Google credentials for the connector and Cloud SQL control plane; roles/cloudsql.client does not by itself log into PostgreSQL. The database still authenticates a database user with a password, or you explicitly enable Cloud SQL IAM database authentication and use a connector/proxy flow that supports it.
    Why not alternatives? We prefer Cloud SQL over a self-hosted database because it offloads operations to Google (automated failover, backups, scaling). Compared to NoSQL options like Firestore or Firebase RTDB, Postgres offers strong consistency and complex relational queries. BigQuery is purely analytic (not suited for OLTP). (If you needed wide-column or global scale, Cloud Spanner could be considered, but it’s more complex and costly.)
  • File/object storage (Cloud Storage): For user-uploaded files, static assets, or backups, use Cloud Storage buckets. It is a durable managed object store, but replication and data residency depend on the bucket location you choose: region, dual-region, or multi-region. Select that location deliberately rather than assuming every bucket is globally replicated. Example: 
    gcloud storage buckets create gs://myapp-prod-files \
    --project=myapp-prod \
    --location=us-central1 \
    --uniform-bucket-level-access
    Then grant your backend SA a Storage role (e.g. roles/storage.objectAdmin) on that bucket. In code you can use the Cloud Storage client, which under the hood uses Workload Identity for auth: 
    from google.cloud import storage
client = storage.Client()
bucket = client.bucket('myapp-prod-files')
blob = bucket.blob('somefile.png')
blob.upload_from_filename('localfile.png')
    Why not alternatives? Cloud Storage is simpler and cheaper for large blobs than, say, storing files in a SQL database. It replaces running a custom file server. We don’t use Firestore or Firebase for file storage. (You could store small JSON data in Firestore, but it is not transactional SQL.) Cloud Storage integrates with other GCP tools (logging, CDN, etc.) and automatically handles encryption and scaling.

Using Workload Identity, both Cloud SQL and Cloud Storage access are secured without embedding keys. The KSA mapping ensures the Pod’s Google SA (with its IAM roles) is used by the Google client libraries.

Deployment Architecture

Our frontend is a React Single-Page App; our backend is a FastAPI microservice.

Frontend on Cloud Run

For a purely static React SPA, Cloud Storage + Cloud CDN, Firebase Hosting, or a managed static host is often the simplest industry-standard deployment. Use Cloud Run when you want a containerized frontend, SSR, a backend-for-frontend, or the same release controls as the rest of your services. If you do containerize the SPA, use reproducible installs and a non-root runtime image:

# Build stage
FROM node:lts-bookworm-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Serve with nginx as a non-root user; pin image digests in production.
FROM nginxinc/nginx-unprivileged:stable-alpine
COPY --from=builder /app/build /usr/share/nginx/html

Build and push the container image. New GCP projects usually use Artifact Registry rather than the older Container Registry-style gcr.io path:

REGION=us-central1
PROJECT_ID=myapp-prod
REPOSITORY=app-images
TAG=2026-05-17

gcloud artifacts repositories create "$REPOSITORY" \
    --repository-format=docker \
    --location="$REGION"

docker build -t "$REGION-docker.pkg.dev/$PROJECT_ID/$REPOSITORY/react-frontend:$TAG" .
docker push "$REGION-docker.pkg.dev/$PROJECT_ID/$REPOSITORY/react-frontend:$TAG"

For production, prefer immutable version tags or image digests over latest. That makes rollbacks and audit trails much easier.

Deploy it to Cloud Run:

gcloud run deploy react-frontend \
    --image us-central1-docker.pkg.dev/myapp-prod/app-images/react-frontend:2026-05-17 \
    --region us-central1 \
    --platform managed \
    --allow-unauthenticated \
    --service-account=frontend-sa@myapp-prod.iam.gserviceaccount.com

--allow-unauthenticated is appropriate for a public marketing site or public SPA shell. For internal/admin frontends, remove it and put Cloud Run behind IAM, Identity-Aware Proxy, or your enterprise IdP.

Cloud Run automatically provisions an HTTPS endpoint for you (for example https://react-frontend-abcd1234-uc.a.run.app). It only serves over HTTPS – HTTP is redirected to HTTPS by default. If you want a custom domain (e.g. www.myapp.com), you can map it in Cloud Run settings.

Set environment variables on the Cloud Run service for any configuration (e.g. the backend API URL or OAuth client ID). Cloud Run containers use the assigned service account (frontend-sa@…) as their identity when calling other GCP services.

Backend on GKE

Create a GKE cluster for the FastAPI service. For example, a Standard cluster with Workload Identity and alias IPs:

gcloud container clusters create my-cluster \
    --region us-central1 \
    --workload-pool=myapp-prod.svc.id.goog \
    --num-nodes=3 \
    --machine-type=e2-standard-4 \
    --enable-ip-alias

This sets up my-cluster with a default node pool of 3 VMs. The --workload-pool flag enables Workload Identity Federation. You could also use a GKE Autopilot cluster (which has WI on by default) to avoid managing nodes at all.

You can add more node pools if desired. For example, to separate workloads:

gcloud container node-pools create backend-pool \
    --cluster=my-cluster \
    --num-nodes=2 \
    --machine-type=e2-medium \
    --node-labels=role=backend

Use node pools to apply different machine types or taints. Always enable IP alias (--enable-ip-alias) to allow private pod ranges.

Deploy your FastAPI app as a Kubernetes Deployment + Service. For example:

apiVersion: apps/v1
kind: Deployment
metadata: { name: fastapi-deployment }
spec:
  replicas: 2
  selector: { matchLabels: { app: fastapi } }
  template:
    metadata: { labels: { app: fastapi } }
    spec:
      serviceAccountName: backend-ksa
      containers:
      - name: fastapi
        image: us-central1-docker.pkg.dev/myapp-prod/app-images/fastapi-backend:2026-05-17
        ports: [ { containerPort: 80 } ]

apiVersion: v1
kind: Service
metadata: { name: fastapi-service }
spec:
  selector: { app: fastapi }
  ports: [ { port: 80, targetPort: 80 } ]

These expose the app on port 80 internally. Note the serviceAccountName: backend-ksa (the K8s SA we annotated earlier); this ensures the pod assumes the Google service account identity.

Ingress and Load Balancing

To expose the backend publicly, create a Kubernetes Ingress (which uses an external HTTP(S) Load Balancer):

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: fastapi-ingress
  annotations:
    kubernetes.io/ingress.class: "gce"
spec:
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: fastapi-service
            port: { number: 80 }

When applied, GKE can provision an external Application Load Balancer with a public IP. The Ingress alone does not automatically prove domain ownership or create a certificate. Reserve the address, point DNS at it, and configure a Google-managed certificate (or Certificate Manager) using the supported GKE annotation/Gateway design. Wait for the certificate to become active before enforcing HTTPS. Make sure the backend permits Google health checks; in a Shared VPC, coordinate the required firewall policy with the host-project administrators.

A browser-hosted SPA normally calls the public GKE endpoint directly. If Cloud Run is acting as an SSR service or backend-for-frontend, it can call that endpoint over HTTPS. For private connectivity, use an internal load balancer and Cloud Run VPC egress. Prefer Direct VPC egress where it is supported; use a Serverless VPC Access connector when its compatibility or topology is required.

Observability and Scaling

Enable Cloud Logging and Monitoring on the cluster (this is on by default in GKE). Export logs via the Kubernetes Logging agent or use aggregated sinks. Define uptime checks and alerts in Cloud Monitoring (for example, an alert if the health endpoint of your service fails). Use horizontal pod autoscaling on the FastAPI Deployment if needed (kubectl autoscale deploy fastapi-deployment --cpu-percent=70 --min=1 --max=5).

Networking and Resource Governance

  • VPC and Subnets: Use a custom VPC (or Shared VPC host) with appropriately sized subnets. Enable Private Google Access when private workloads need supported Google APIs without external IP addresses. Configure Cloud SQL private IP separately through private services access or the supported Private Service Connect topology. The GKE metadata server is link-local and governed separately. Use hierarchical firewall policies for organization/folder defaults while allowing required DNS, metadata, health-check, control-plane, and application traffic. If using Shared VPC, the host project owns the network and service projects attach workloads to it.
  • Project-level Security: Disable overly broad Org policies like automatic Editor grants for default SAs. Regularly audit IAM policies (Cloud IAM Recommender can surface over-privileged identities). Use Google Groups for role assignments (e.g. “DevOps” group with Compute Admin on dev, but Cloud SQL Client on prod).
  • Networking Security: Consider enabling VPC Service Controls if you need to protect against data exfiltration from managed services. At a minimum, configure Kubernetes Network Policies to restrict traffic between pods if you run multiple services.
  • Cost and Billing: Since billing is at the project level, use separate projects (or folders) per environment to track costs. Use billing reports or Cloud Billing budget alerts to monitor spend. Tag resources (with labels like env=prod) and set up budgets per tag. Regularly clean up unused resources (old node pools, images, volumes) to control costs. Consider using Cloud Budgets with alerts on 50%/75%/90% spend thresholds.
  • VPC Quotas and Limits: Use VPC native clusters (alias IP) to avoid exhaustion of IPs. Plan subnet sizes for pods and services, anticipating scale. For example, if you expect 100 Pods per node pool, allocate a /14 for pod range. Use Cloud NAT if your nodes need to access the Internet without external IPs.
  • DNS and TLS: Use Cloud DNS (or your provider) for domain names. For Cloud Run, GKE Ingress, or Gateway, use the product’s supported Google-managed certificate integration or Certificate Manager. “ACM” commonly refers to AWS Certificate Manager and is not the Google Cloud product name.

By following these steps and best practices, you’ll have a robust GCP foundation: isolated projects and IAM, secure service identities (Workload Identity) for accessing Cloud SQL and Storage, user login via Google OIDC in the React app, and autoscaled deployments of your frontend and backend on Cloud Run and GKE. All communication is over HTTPS, and data access from code is locked down to specific service accounts with minimal privileges. This architecture is production-ready and scalable for an enterprise SaaS with Google Workspace authentication.
