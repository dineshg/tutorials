SSO, OAuth 2.0, and OpenID Connect: The Identity Primer

Authentication terminology feels confusing because several layers happen during one click on “Sign in.” This chapter separates the user experience, delegation protocol, identity protocol, browser session, and API authorization before the next chapter implements the complete flow in React and FastAPI.

The three-sentence model
  • SSO is the experience: authenticate once with a trusted identity provider and use more than one application without entering credentials again.
  • OAuth 2.0 is delegated authorization: a client obtains an access token that lets it call a resource server within an approved scope.
  • OpenID Connect (OIDC) adds authentication: it standardizes how a client learns which user authenticated, principally through an ID token with identity claims.

1) Start with the problem: applications should not collect every password

Suppose your company has ten internal applications. Without federation, every application could create its own username and password database. That produces ten password stores, ten account-recovery processes, and ten opportunities to implement authentication badly.

A better design delegates authentication to an identity provider (IdP), such as Microsoft Entra ID, Google Identity, Okta, or an internal standards-compliant provider. The application redirects the user to the IdP. The IdP handles credentials, passkeys, MFA, risk checks, and account policy, then returns a cryptographically verifiable result to the application.

Visual: one sign-in, separate trust boundaries

The IdP authenticates the user. The API still makes its own authorization decision for each request.

2) SSO is an outcome, not a token format

Single sign-on means the user can move between trusted applications without repeatedly entering credentials. It is an experience created by a shared IdP session and federation protocols. SSO is not itself an API protocol and does not tell your FastAPI endpoint which records the caller may access.

When the user signs in to App A, the IdP may create its own secure browser session. Later, App B redirects the same browser to the IdP. The IdP recognizes its session, may skip the credential prompt, and completes a new authorization flow for App B. Each application still receives tokens intended for that application; one universal token should not be replayed everywhere.

3) OAuth 2.0 delegates access to an API

OAuth separates four roles. Keeping these roles distinct prevents most terminology mistakes:

OAuth roleIn this book's exampleResponsibility
Resource ownerThe signed-in userOwns or is authorized to act on protected data.
ClientReact app or backend-for-frontendRequests delegated access; it is not the API being protected.
Authorization serverThe IdPAuthenticates, obtains consent/policy approval, and issues tokens.
Resource serverFastAPIValidates an access token and authorizes the requested operation.

The client asks for scopes such as documents:read. The authorization server may issue an access token. The client sends that token to the API using Authorization: Bearer <access-token>. The API validates the token's signature or introspection result, issuer, audience, expiry, and relevant authorization claims before serving data.

OAuth alone is not a login protocol. An access token is addressed to a resource server and represents delegated API access. Treating arbitrary access-token contents as a portable user profile couples the client to one provider and can create token-substitution vulnerabilities.

4) OIDC adds a standard authentication result

OpenID Connect is an identity layer on top of OAuth 2.0. The client requests the openid scope. After the user authenticates, the client receives an ID token intended for the client. The ID token says who authenticated, which issuer authenticated them, which client it was issued to, and when that authentication result expires.

{
  "iss": "https://idp.example.com",
  "sub": "00u123stable-subject",
  "aud": "web-client-id",
  "exp": 1785400000,
  "iat": 1785396400,
  "nonce": "request-bound-random-value",
  "email": "alice@example.com"
}

The durable external identity key is normally the pair (iss, sub). Email addresses can change, be recycled, or be absent. Store the issuer and subject when mapping the external identity to your internal user_id.

5) Keep ID tokens, access tokens, refresh tokens, and sessions separate

A backend-for-frontend (BFF) can keep OAuth tokens server-side and give the browser only a hardened session cookie. A pure SPA can use Authorization Code with PKCE, but must account for browser token-theft risk and should avoid persistent storage when the architecture allows it.

6) Why Authorization Code with PKCE is the default teaching flow

The browser does not receive tokens directly from the authorization endpoint. It receives a short-lived, single-use authorization code. The client then exchanges that code at the token endpoint. PKCE binds the code to a secret value created for that particular authorization attempt:

  1. The client generates a random code_verifier.
  2. It sends a derived code_challenge with the authorization request.
  3. The IdP authenticates the user and redirects back with a code.
  4. The client sends the original verifier when exchanging the code.
  5. The authorization server checks that the verifier matches the earlier challenge before issuing tokens.

PKCE limits the usefulness of a stolen authorization code. It does not replace redirect-URI validation, state for request correlation and CSRF defense, OIDC nonce validation, TLS, or secure token storage.

7) Authentication is not application authorization

After token validation, your application still decides what the caller may do. A valid login does not automatically grant access to every tenant, document, or administrative operation.

Imagine a company building with a receptionist.

  • OAuth 2.0 is a visitor pass that grants access to specific rooms: it is delegated authorization.
  • OIDC adds a verified identity badge: the client can establish who signed in.
  • Your application policy is the door controller for each room: it checks tenant membership, role, ownership, and operation.

Scopes express what an access token permits at an API boundary. Roles and groups are organizational inputs. Tenant membership and resource ownership are application data. Your authorization layer may combine all of them, but they are not interchangeable.

8) Common mistakes and the correct mental model

MistakeCorrection
“OAuth logs the user in.”OAuth delegates API access; OIDC standardizes authentication on top of it.
“SSO means one token works for every app.”SSO normally reuses the IdP session while issuing audience-specific results to each client/resource.
“The API should accept the ID token.”The API normally accepts an access token whose audience/resource identifies that API.
“Email is the user ID.”Use the issuer and subject as the external stable key; treat email as a mutable attribute.
“A valid token means the request is authorized.”Token validation authenticates the credential; application policy still authorizes the operation and resource.
“JWT validation means decoding the payload.”Decoding is not trust. Verify signature, issuer, audience, expiry, and required claims.
