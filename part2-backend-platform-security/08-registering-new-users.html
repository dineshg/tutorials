First Login and User Provisioning

6 min read·6 sections
On this page
1. New User Sign-In Flow (React + Google OIDC + FastAPI)2. Example FastAPI Endpoint for User Provisioning3. Where "Registration" Actually Lives4. Choose a Provisioning Policy Explicitly5. Make First Login Race-Safe6. Sign-In Is Ongoing Reconciliation

Authentication proves an external identity; provisioning creates the application account, tenant membership, and starting authorization state.

Where this fits The preceding chapters established OIDC Authorization Code with PKCE and API token validation. This chapter begins after a token has been validated. It explains just-in-time provisioning without confusing an identity-provider account, an application user, and a tenant membership.

Assume the organisation's Google Workspace policy already allows this person to authenticate. That permission does not by itself grant access to this application or any tenant data.

1. New User Sign-In Flow (React + Google OIDC + FastAPI)

Key idea: The login page doesn't "register" the user with Google—Google already knows them. Your app "registers" the user by provisioning a record in your database the first time your backend sees a valid identity.
  1. User clicks "Sign in with Google"

    React starts OIDC Authorization Code + PKCE by redirecting the browser to Google's authorization endpoint.

    Outcome: user authenticates with Google (SSO).

  2. The registered client completes the code exchange

    In a browser-only public-client design, React can exchange the authorization code using its PKCE verifier and keep tokens in memory. In a backend-for-frontend design, the backend completes the exchange and gives the browser an HTTP-only session cookie.

    The credential sent to your API must be an access token issued for that API's audience. An OIDC ID token describes the login result for its client; it is not a general-purpose API bearer token. A Google-only application may instead validate the login at its backend and mint an application session.

  3. React calls a bootstrap endpoint on your API

    Right after login, the frontend calls something like:

    • POST /auth/bootstrap for an operation that may create or update application records, then
    • GET /me for later read-only profile retrieval.

    with:

    Authorization: Bearer <access_token>

    Purpose: let the backend validate the token and decide what to do with this identity.

  4. FastAPI validates token and extracts stable identity

    Backend verifies the token (signature + issuer/audience/expiry), then reads claims like:

    • sub → stable user identifier at this IdP
    • email and email_verified → optional policy inputs, never the stable primary key
  5. Backend checks if the user already exists in your DB

    Backend looks up by a stable key like (issuer, sub) (best practice), optionally storing email too.

    Case A: user exists

    • Return user profile + tenant info.
    • Frontend proceeds normally.

    Case B: user is new

    • This is where "registration" happens (provisioning).

2. Example FastAPI Endpoint for User Provisioning

This endpoint is the bootstrap call that validates the Bearer token, looks up the user, creates the DB row if missing, and returns user details.

The code below is a teaching scaffold. The industry-standard version verifies the token against JWKS/OIDC discovery, stores users in a real database with a unique constraint on (issuer, subject), performs the create-or-return logic in a transaction/upsert, and records audit fields such as created_at and last_login_at.

from fastapi import FastAPI, Depends, HTTPException
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from pydantic import BaseModel
from datetime import datetime, timezone

app = FastAPI()
bearer = HTTPBearer(auto_error=True)

class BootstrapResponse(BaseModel):
    user_id: str
    tenant_id: str
    is_new_user: bool

	# --- Teaching-only in-memory store (production: Postgres/Cloud SQL) ---
USERS_BY_ISS_SUB: dict[tuple[str, str], dict] = {}  # key = (issuer, sub)

	# --- Teaching-only token verifier (production: JWT/JWKS validation) ---
def verify_and_decode_access_token(token: str) -> dict:
    """
	    Production implementation:
	      - verify JWT signature using Google JWKS
	      - check issuer (iss), audience (aud), expiry (exp)
	      - optionally check nonce/azp/scopes depending on token type
	    This teaching version returns mock claims so you see where they come from.
    """
    # demo-alice-token is only a classroom stand-in for an already-verified JWT.
    if token == "demo-alice-token":
        return {
            "iss": "https://accounts.google.com",
            "sub": "user-A-sub",
            "email": "alice@acme.com",
            "email_verified": True,
        }
    raise HTTPException(status_code=401, detail="Invalid/expired token")

def map_email_to_tenant_id(email: str) -> str:
    """
    Example tenant mapping policy: email domain -> tenant.
    (Alternative policies: invite-only lookup, explicit claim, etc.)
    """
    domain = email.split("@")[-1].lower()
    if domain == "acme.com":
        return "tenant-acme"
    raise HTTPException(status_code=403, detail="No tenant mapping for this user")

@app.post("/auth/bootstrap", response_model=BootstrapResponse)
def auth_bootstrap(creds: HTTPAuthorizationCredentials = Depends(bearer)):
    # 1) Extract raw token from "Authorization: Bearer <token>"
    token = creds.credentials

    # 2) Validate + decode -> claims (iss/sub/email)
    claims = verify_and_decode_access_token(token)
    issuer = claims["iss"]
    sub = claims["sub"]
    email = claims.get("email", "")
    if not claims.get("email_verified", False):
        raise HTTPException(status_code=403, detail="Verified email required")

    # 3) Look up user by stable key (issuer, sub)
    key = (issuer, sub)
    existing = USERS_BY_ISS_SUB.get(key)

    if existing:
        # User already provisioned
        return BootstrapResponse(
            user_id=existing["user_id"],
            tenant_id=existing["tenant_id"],
            is_new_user=False,
        )

    # 4) New user -> determine tenant_id (domain/invite/etc.)
    tenant_id = map_email_to_tenant_id(email)

    # 5) "Register" user in DB (provision)
    user_row = {
        "user_id": f"db-user-{sub}",  # in real DB: UUID
        "tenant_id": tenant_id,
        "issuer": issuer,
        "sub": sub,
        "email": email,
        "created_at": datetime.now(timezone.utc).isoformat(),
    }
    USERS_BY_ISS_SUB[key] = user_row

    return BootstrapResponse(
        user_id=user_row["user_id"],
        tenant_id=user_row["tenant_id"],
        is_new_user=True,
    )
  1. Provision the user (your app's "registration")

    The backend creates the required records:

    1. Determine tenant_id
      • Domain mapping: alice@acme.com → tenant "acme"
      • or invite-only: user must already be linked to a tenant
      • or self-serve tenant creation (first user creates tenant)
    2. Create user row
      • Store: issuer, sub, email, tenant_id, timestamps
    3. Optional defaults
      • Preferences, empty workspace, default roles, etc.
  2. Backend returns a bootstrap response

    Example:

    {
  "user_id": "…",
  "tenant_id": "…",
  "is_new_user": true
}

    React can now show an onboarding / "upload documents" screen.

3. Where "Registration" Actually Lives

  • Google authenticates the user.
  • Your backend decides whether the identity is allowed and attaches it to a tenant.
  • "Registration" = your DB provisioning, not creating credentials.

4. Choose a Provisioning Policy Explicitly

PolicyHow a new identity becomes a userUse when
Invite onlyA pending invitation already binds an email or subject to a tenant and initial role.Controlled B2B and regulated applications.
Just in time (JIT)A verified identity that satisfies policy is created during first login.Managed workforce domains with clear admission rules.
SCIM / directory syncAn identity-management system creates, updates, and disables users before login.Enterprise lifecycle automation and rapid deprovisioning.
Self-service tenant creationThe first allowed user creates a tenant and becomes its initial administrator.SaaS onboarding with abuse controls and verification.

Domain mapping such as @acme.com → tenant-acme is a teaching example, not a universal policy. Use it only with a verified email, an owned-domain registry, and an explicit business rule. Invitations or directory-managed membership are safer when the same domain can contain people who must not share application data.

5. Make First Login Race-Safe

Browsers retry, users double-click, and multiple tabs can call bootstrap simultaneously. An in-memory check followed by an insert is not sufficient in production. Put a unique constraint on (issuer, subject) and perform an upsert or transaction: 

INSERT INTO app_user (issuer, subject, email, status, created_at)
VALUES (:issuer, :subject, :email, 'active', CURRENT_TIMESTAMP)
ON CONFLICT (issuer, subject)
DO UPDATE SET
    email = EXCLUDED.email,
    last_login_at = CURRENT_TIMESTAMP
RETURNING user_id, status;

Tenant membership should have its own unique key, such as (tenant_id, user_id). Keeping identity and membership separate supports users who legitimately belong to more than one tenant and avoids treating tenant data as an attribute permanently embedded in the identity-provider account.

6. Sign-In Is Ongoing Reconciliation

The second login is not simply "do nothing." Update safe profile metadata such as display name, verified email, and last_login_at; evaluate whether the application user or membership is suspended; and apply current authorization policy. Never silently reactivate a locally disabled user merely because the identity provider authenticated them.

  • Use (iss, sub) as the external identity key; email addresses can change or be reassigned.
  • Model user status and membership status separately: invited, active, suspended, or removed.
  • Decide whether group and role changes are read on every login, synchronized by SCIM, or maintained locally.
  • Record provisioning, membership changes, denial reasons, and the policy version in an audit trail.
  • Define deprovisioning and session revocation; login is only one part of the account lifecycle.
Correct mental model The identity provider owns credentials and authentication. Your application owns admission, the internal user record, tenant memberships, roles, and data authorization.
