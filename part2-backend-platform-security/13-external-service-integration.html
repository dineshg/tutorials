Part II - Backend, Platform & Security

Calling External Services Across Cloud Trust Boundaries

6 min read·7 sections
On this page
1. Option A: API Key Stored in GCP Secret Manager2. Option B: Microsoft Entra Workload Identity Federation3. How This Relates to Service Accounts4. Reliability Rules Shared by Both Options5. Data Governance and Observability6. Decision SummaryOfficial References

A GCP workload calling Azure OpenAI needs an Azure-accepted credential, a bounded network client, and a clear data-governance contract.

Where this fits Chapter 12 separated end-user identity, application authorization, and workload identity. This chapter follows the workload across a cloud boundary. The end user's bearer token still authorizes the application request, but the backend uses its own credential to call Azure.

There are two production patterns. Choose from policy and operational requirements rather than assuming that the most complex option is always best.

QuestionAPI key in Secret ManagerEntra workload federation
Long-lived Azure credentialYes; rotate and version it.No; exchange a trusted external assertion for a short-lived token.
Initial setupLower.Higher: app registration, federated credential, RBAC, and token exchange.
Runtime dependenciesGCP IAM + Secret Manager + Azure endpoint.Google token issuer + Entra token endpoint + Azure endpoint.
Best fitSmaller systems with mature secret rotation.Higher-assurance systems that prohibit static cross-cloud credentials.

1. Option A: API Key Stored in GCP Secret Manager

Flow

  1. Your backend (running on GKE) authenticates to GCP Secret Manager using its GCP service account (Workload Identity).
  2. It reads the Azure OpenAI API key from Secret Manager.
  3. It calls Azure OpenAI with:
    • api-key: <key> header (typical for Azure OpenAI)

Why choose this

  • Easiest to implement
  • No Azure identity federation complexity
  • Common and reliable

What you “associate”

1) Store the secret

  • Secret: azure-openai-api-key

2) Grant your backend service account access to read it

  • IAM: give backend-sa@... role roles/secretmanager.secretAccessor on that secret.

3) In code: load once, reuse the HTTP client, and call Azure

import os
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI, Request
from google.cloud import secretmanager


def read_secret(secret_id: str, version: str) -> str:
    client = secretmanager.SecretManagerServiceClient()
    name = (
        f"projects/{os.environ['GCP_PROJECT']}/secrets/"
        f"{secret_id}/versions/{version}"
    )
    response = client.access_secret_version(request={"name": name})
    return response.payload.data.decode("utf-8")


class AzureOpenAIClient:
    def __init__(self, *, api_key: str, endpoint: str, deployment: str):
        self._deployment = deployment
        self._http = httpx.AsyncClient(
            base_url=endpoint.rstrip("/"),
            headers={"api-key": api_key},
            timeout=httpx.Timeout(connect=5.0, read=60.0, write=15.0, pool=5.0),
            limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
        )

    async def create_response(self, prompt: str) -> dict:
        response = await self._http.post(
            "/openai/v1/responses",
            json={"model": self._deployment, "input": prompt},
        )
        response.raise_for_status()
        return response.json()

    async def close(self) -> None:
        await self._http.aclose()


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Secret access is synchronous, but startup completes before requests run.
    # Pin a deployed version so rollback is deterministic.
    api_key = read_secret(
        "azure-openai-api-key",
        os.environ["AZURE_OPENAI_KEY_VERSION"],
    )
    app.state.azure_openai = AzureOpenAIClient(
        api_key=api_key,
        endpoint=os.environ["AZURE_OPENAI_ENDPOINT"],
        deployment=os.environ["AZURE_OPENAI_DEPLOYMENT"],
    )
    yield
    await app.state.azure_openai.close()


app = FastAPI(lifespan=lifespan)


@app.post("/generate")
async def generate(request: Request, prompt: str) -> dict:
    return await request.app.state.azure_openai.create_response(prompt)

Microsoft Foundry exposes several API surfaces. The example uses the current OpenAI-compatible /openai/v1/responses shape. Older deployment-scoped routes use an explicit api-version query parameter. Treat endpoint paths, supported models, and API versions as deployed configuration checked against the current Azure documentation.

Reading Secret Manager on every model call adds latency and another failure point. Load a pinned version at startup, inject a mounted secret through your platform, or use a controlled refresh mechanism. Rotate by creating a new secret version, deploying the new version reference, verifying it, and then disabling the old version.

2. Option B: Microsoft Entra Workload Identity Federation

Flow

  1. Your backend runs as a specific Kubernetes/Google service account through Workload Identity Federation for GKE.
  2. The workload obtains a Google-signed OIDC assertion with the audience expected by the Entra federated credential.
  3. Microsoft Entra validates the assertion's issuer, subject, audience, and signature against the configured trust.
  4. The workload exchanges that assertion for a short-lived Entra access token scoped to Azure AI.
  5. It calls Azure OpenAI with Authorization: Bearer <access_token>.

What must be configured

  1. Create an Entra app registration (or supported managed identity) and its service principal.
  2. Add a federated identity credential whose issuer, subject, and audience exactly match the Google assertion. Microsoft's Google Cloud example uses issuer https://accounts.google.com, the Google service account's unique ID as subject, and api://AzureADTokenExchange as audience.
  3. Assign only the Azure role required for inference, commonly Cognitive Services OpenAI User, at the narrowest useful scope.
  4. Configure the workload with the Entra tenant ID, application client ID, Azure scope, endpoint, and model deployment; none of these values is a secret.
# Protocol-level outline. Production code should use a supported credential
# library or a well-tested exchange component rather than duplicating OAuth.
external_assertion = obtain_google_oidc_assertion(
    audience="api://AzureADTokenExchange"
)

token_response = await http.post(
    f"https://login.microsoftonline.com/{tenant_id}/oauth2/v2.0/token",
    data={
        "client_id": entra_client_id,
        "grant_type": "client_credentials",
        "scope": "https://cognitiveservices.azure.com/.default",
        "client_assertion_type": (
            "urn:ietf:params:oauth:client-assertion-type:jwt-bearer"
        ),
        "client_assertion": external_assertion,
    },
)
token_response.raise_for_status()
azure_access_token = token_response.json()["access_token"]

result = await http.post(
    f"{azure_endpoint}/openai/v1/responses",
    headers={"Authorization": f"Bearer {azure_access_token}"},
    json={"model": deployment, "input": prompt},
)

Why choose this

  • No long-lived API keys
  • Short-lived tokens, easier to rotate
  • Stronger enterprise security posture

Tradeoffs

  • More setup (Azure app registration, federated identity config, token exchange logic)
  • Slightly more moving parts than API keys

3. How This Relates to Service Accounts

Important:

  • Your GCP service account gives you permission to read GCP secrets/logs/etc.
  • Azure doesn’t care about GCP service accounts. Azure cares about Azure identity (or API keys).
  • So you either:
    • use GCP SA → read API key → call Azure (Option A), or
    • configure federation so your workload can mint Azure tokens (Option B)

4. Reliability Rules Shared by Both Options

  • Reuse clients and connections: create one bounded HTTP client per process, not one client per request.
  • Set phase-specific timeouts: connect, pool acquisition, write, and read can fail for different reasons.
  • Retry selectively: retry connection failures, selected 429 responses, and selected 5xx responses with server guidance, exponential backoff, jitter, and a strict attempt budget. Do not retry ordinary 400/401/403 errors unchanged.
  • Bound concurrency: use connection limits, rate limits, and admission control so Azure throttling does not become an internal retry storm.
  • Preserve deadlines: an outbound timeout must fit inside the remaining inbound request deadline.
  • Make effects idempotent: model inference is normally read-like, but tool calls or downstream writes triggered from a response need explicit idempotency controls.

5. Data Governance and Observability

Authentication answers whether the workload may call Azure. It does not decide whether the prompt may contain a customer's data. Before crossing the boundary, classify the payload and enforce residency, retention, encryption, private networking/egress, content logging, and contractual requirements.

  • Send only the fields required for the model task; redact secrets and unnecessary personal data.
  • Log request IDs, tenant IDs, deployment names, token counts, latency, status class, retry count, and policy decisions, but never credentials or full sensitive prompts by default.
  • Separate caller authorization from provider credentials in traces so audit records show both the initiating user and executing workload.
  • Alert on authentication failures, sustained throttling, latency percentiles, model/deployment drift, and unusual per-tenant usage.

6. Decision Summary

Choose the simplest option that satisfies policy Use a versioned Secret Manager API key when your organization accepts managed static credentials and can rotate them reliably. Use Entra federation when eliminating long-lived cross-cloud secrets justifies the extra trust configuration and token-exchange dependency.
