Modern Auth Additions: Passkeys, DPoP, mTLS, Token Exchange

Why this chapter exists Chapters 6–9 in this Part cover the bedrock — bearer tokens, OAuth2, OIDC, PKCE, JWT vs opaque, JWKS. This 2026 supplement covers four controls now commonly assessed in enterprise designs. It uses RFC 9700 as the finalized OAuth 2.0 security baseline; OAuth 2.1 remains an active Internet-Draft. This chapter is a focused supplement, not a replacement.

1) Passkeys / WebAuthn — replacing passwords for human login

A passkey is a WebAuthn credential bound to the user's device (or a synced keychain like iCloud Keychain / Google Password Manager / 1Password). Instead of typing a password, the browser uses public‑key cryptography over a challenge issued by your server. The private key never leaves the authenticator; only a signed assertion comes back.

Why prefer passkeys over passwords (and even over TOTP)

  • Phishing‑resistant: the credential is bound to your origin (rp.id), so a fake site cannot trigger a usable signature.
  • No shared secret on the server: you store only a public key. A database breach exposes nothing reusable.
  • Less dependence on password reset: a synced passkey can follow the user through the platform credential provider. Device-bound credentials, lost authenticators, account takeover, and bootstrap for a new device still require an explicit recovery and re-enrolment policy.

Where it sits relative to OIDC

You typically still use OIDC for SSO across apps; passkeys replace the password step at the Identity Provider. Major identity providers, including Google, GitHub, Microsoft Entra, Okta, and Auth0, support passkeys in their current authentication offerings, although enrolment, recovery, and passwordless-policy options differ. The downstream OAuth2/OIDC flow is unchanged from Chapter 7.

Minimal server skeleton (FastAPI + py_webauthn)

# pip install webauthn fastapi
from fastapi import FastAPI, HTTPException
from webauthn import (
    generate_registration_options, verify_registration_response,
    generate_authentication_options, verify_authentication_response,
)
from webauthn.helpers.structs import (
    PublicKeyCredentialDescriptor, AuthenticatorSelectionCriteria,
    UserVerificationRequirement,
)

app = FastAPI()
RP_ID   = "example.com"
RP_NAME = "Example Corp"
ORIGIN  = "https://example.com"

USERS = {}        # user_id -> {"name": ..., "credentials": [...]}
CHALLENGES = {}   # user_id -> current challenge bytes

@app.post("/webauthn/register/options")
def reg_options(user_id: str, username: str):
    opts = generate_registration_options(
        rp_id=RP_ID, rp_name=RP_NAME,
        user_id=user_id.encode(), user_name=username,
        authenticator_selection=AuthenticatorSelectionCriteria(
            user_verification=UserVerificationRequirement.PREFERRED,
            resident_key="required",   # creates a discoverable passkey
        ),
    )
    CHALLENGES[user_id] = opts.challenge
    USERS.setdefault(user_id, {"name": username, "credentials": []})
    return opts            # browser calls navigator.credentials.create() with this

@app.post("/webauthn/register/verify")
def reg_verify(user_id: str, attestation: dict):
    verification = verify_registration_response(
        credential=attestation,
        expected_challenge=CHALLENGES[user_id],
        expected_origin=ORIGIN,
        expected_rp_id=RP_ID,
    )
    USERS[user_id]["credentials"].append({
        "id":         verification.credential_id,
        "public_key": verification.credential_public_key,
        "sign_count": verification.sign_count,
    })
    return {"ok": True}

The login side is symmetric: you call generate_authentication_options(...), send the resulting challenge to the browser, and verify the assertion with the public key you stored at registration.

The skeleton omits production state management A WebAuthn challenge must be random, one-time, short-lived, and bound to the intended user or anonymous ceremony session. Consume it atomically after verification. Store credentials durably, validate user-verification policy, update the signature counter where the authenticator supplies one, rate-limit ceremonies, and design recovery so it is not weaker than the passkey.
Production reality Almost no one writes the server primitives by hand anymore. In an enterprise stack you turn passkeys on at the IdP (Entra / Okta / Auth0 / Keycloak) and your FastAPI app keeps using OIDC unchanged. The snippet above is for understanding what the IdP does.

2) DPoP — sender‑constrained access tokens (RFC 9449)

A plain bearer token (Chapter 9) is like cash: whoever holds it can spend it. If a token leaks via logs, a misconfigured proxy, or an XSS bug, the attacker gets full access until expiry. DPoP (Demonstrating Proof‑of‑Possession) binds the token to a key pair the client holds, so a stolen token is useless without the private key.

How a DPoP request looks

POST /api/v1/orders HTTP/1.1
Host: api.example.com
Authorization: DPoP eyJhbGciOiJSUzI1NiIs...<access_token>
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2In0.<proof_jwt>

Two headers are sent:

  • Authorization: the access token, prefixed with DPoP instead of Bearer.
  • DPoP: a short‑lived JWT, signed with the client's private key, whose payload includes the HTTP method (htm), request URL (htu), issued-at time (iat), and unique proof ID (jti). A protected-resource proof also includes a hash of the access token (ath). A nonce is included when the authorization or resource server has issued one; it is not present in every proof.

At token issuance, the AS records the JWK thumbprint of the client's public key inside the access token's cnf.jkt claim. The resource server verifies that the DPoP proof was signed by that exact key, that the htm/htu match this request, that jti has not been replayed during the acceptance window, and that the proof is fresh.

Validating DPoP in FastAPI (sketch)

import base64, hashlib, time, jwt   # PyJWT
from fastapi import Header, HTTPException, Request
from jwt import PyJWK

def b64url(value: bytes) -> str:
    return base64.urlsafe_b64encode(value).rstrip(b"=").decode()

async def require_dpop(
    request: Request,
    authorization: str = Header(...),
    dpop: str = Header(...),
):
    if not authorization.startswith("DPoP "):
        raise HTTPException(401, "Expected DPoP scheme")
    access_token = authorization.removeprefix("DPoP ")

    # 1) Inspect the JOSE header, but never let it choose any algorithm.
    header = jwt.get_unverified_header(dpop)
    if header.get("typ") != "dpop+jwt" or header.get("alg") != "ES256":
        raise HTTPException(401, "unsupported DPoP header")
    public_jwk = header.get("jwk", {})
    if not public_jwk or "d" in public_jwk:
        raise HTTPException(401, "invalid public JWK")

    # 2) Verify with a server allowlist and require protocol claims.
    proof_key = PyJWK.from_dict(public_jwk, algorithm="ES256").key
    proof = jwt.decode(
        dpop,
        proof_key,
        algorithms=["ES256"],
        options={"verify_aud": False},
        require=["htm", "htu", "iat", "jti"],
    )

    # 3) Bind to the externally visible canonical request URI and method.
    if proof["htm"].upper() != request.method:
        raise HTTPException(401, "htm mismatch")
    if proof["htu"] != canonical_public_uri(request):
        raise HTTPException(401, "htu mismatch")
    if abs(time.time() - proof["iat"]) > 60:
        raise HTTPException(401, "stale proof")
    if not await replay_cache.mark_once(proof["jti"], ttl_seconds=120):
        raise HTTPException(401, "replayed proof")

    # 4) Bind proof to this access token.
    ath_expected = b64url(hashlib.sha256(access_token.encode()).digest())
    if proof.get("ath") != ath_expected:
        raise HTTPException(401, "ath mismatch")

    # 5) Validate access token normally, then compare its key thumbprint.
    claims = verify_access_token(access_token)  # signature, iss, aud, exp
    if claims.get("cnf", {}).get("jkt") != jwk_thumbprint(public_jwk):
        raise HTTPException(401, "token not bound to this key")

    # 6) If the server issued a DPoP-Nonce, verify proof["nonce"] here.
    return claims

This remains a teaching sketch: use an authorization-server/resource-server library that implements RFC 9449 where possible. Behind a reverse proxy, construct canonical_public_uri only from trusted forwarding configuration; accepting arbitrary Forwarded headers lets a client choose the value you compare. DPoP reduces bearer-token replay, but it does not protect a client whose private key and token are both stolen by XSS, malware, or a compromised runtime.

When to adopt DPoP

  • Public clients (SPAs, mobile apps) that cannot be issued mTLS certs.
  • High‑sensitivity APIs (payments, admin) where bearer leakage is unacceptable.
  • MCP servers that accept tokens forwarded from a host — see Part III.

3) mTLS — sender‑constrained tokens for service‑to‑service (RFC 8705)

For workload‑to‑workload calls inside your platform (Chapter 10 / 11), mutual TLS is another sender-constraining mechanism. The calling service presents an X.509 client certificate during the TLS handshake. In the specific RFC 8705 OAuth profile, the authorization server binds an issued access token to the certificate's hash through cnf.x5t#S256.

The flow

  1. Workload requests a token from the AS over mTLS.
  2. AS records the SHA‑256 thumbprint of the client cert in cnf.x5t#S256.
  3. Workload calls the resource server also over mTLS with the same cert.
  4. Resource server verifies that the cert hash from the TLS layer matches the cnf.x5t#S256 claim in the token.

Where it fits in your reference architecture

This is a strong match for the “workload identity” boundary already covered in Chapter 10 (end‑user vs workload identity) and Chapter 11 (GCP workload identity). SPIFFE/SPIRE can issue X.509 SVIDs, and a service mesh such as Istio can enforce transport mTLS. That does not automatically turn an OAuth token into an RFC 8705 certificate-bound token: the authorization server and resource server must explicitly implement the RFC 8705 binding and compare it with the certificate authenticated at the protected endpoint.

4) OAuth 2.0 Token Exchange (RFC 8693) — propagating the user downstream

The classic question from Chapter 10: "My user calls FastAPI with their OIDC token. FastAPI then calls a downstream API that needs the user's identity, not FastAPI's. How do I forward identity safely?"

A standards-based option is OAuth 2.0 Token Exchange. FastAPI asks the authorization server to exchange the inbound user token for a new, downstream-audience token with narrower scope:

POST /oauth/token HTTP/1.1
Host: idp.example.com
Authorization: Basic <FastAPI client credentials>
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<the inbound user access token>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&audience=https://crm.example.com
&scope=crm.read

If the authorization server's policy permits the exchange, it returns a new access token whose:

  • sub and delegated-subject semantics follow the authorization server's policy rather than being assumed to copy unchanged,
  • aud is the downstream API,
  • act can record FastAPI as the current actor when the authorization server represents delegation that way, allowing the downstream API to audit “subject X via service Y.”
Anti‑pattern alert Forwarding the inbound user token verbatim to a downstream API is the most common mistake. It works, but the downstream API now sees a token whose aud claim is your service, which a good resource server will reject. Token exchange (RFC 8693) is one standards-based fix when both authorization and resource servers support it. Microsoft Entra's on-behalf-of (OBO) flow addresses the same delegation problem through its provider-specific contract.

5) Quick decision matrix

BoundaryUseWhy
Human → Browser → Your app OIDC + Passkeys at the IdP, PKCE for the app Phishing‑resistant, no passwords stored.
Browser/SPA/mobile → Your API OIDC + DPoP access tokens Token-only replay is blocked; full client compromise remains in scope.
Workload → Workload (inside platform) mTLS + cert‑bound tokens (cnf.x5t#S256) Strong binding when the OAuth and TLS layers implement RFC 8705 together.
Workload → Workload (across orgs) Workload Identity Federation (Chapter 11) + signed JWT assertion No long‑lived secrets to rotate.
Your API → Downstream API on user's behalf Token exchange (RFC 8693) / OBO Preserves user identity, narrows audience, records the actor.
