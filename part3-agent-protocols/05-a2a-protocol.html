A2A 1.0: Agent Discovery, Delegation, and Long-Running Tasks

The previous chapters used MCP to expose tools and context to an AI host. A2A addresses the next boundary: one autonomous agent delegates work to another autonomous agent without depending on the other agent's internal framework, memory, model, or tools. We will build the idea from a simple message into discovery, task state, multi-turn input, artifacts, streaming, security, and a purchasing-concierge implementation.

1) What A2A is (the mental model)

A2A is a standard way for agents, rather than only tools, to communicate with each other over a network. The important word is “agents”: each participant is allowed to be autonomous, stateful, long-running, and potentially opaque internally. A2A does not require agents to share their chain-of-thought, private memory, or internal tools. Instead, they collaborate via a shared external protocol.

An agent wants help → it finds another agent → it delegates work as a Task → it receives Messages and Artifacts → it continues / completes the Task.
One-line mental model: A2A is structured messages, discoverable capabilities, and a durable task lifecycle for collaboration across vendors, frameworks, and deployments.
Version used in this chapter The normative examples target stable A2A 1.0. The protocol defines one canonical data model and three standard bindings: JSONRPC, GRPC, and HTTP+JSON. The HTTP+JSON examples send A2A-Version: 1.0 and use application/a2a+json.

2) Why A2A exists (problems it solves)

Problem 1: Agents live in silos

One team builds an agent with Framework A, another team builds a specialist agent with Framework B, a third vendor provides a hosted agent. Without a common “language,” collaboration becomes bespoke glue code.

Problem 2: Work is long-running and multi-turn

Real workflows have approvals, waiting on humans, retries, partial progress, streaming updates, and artifacts (files, forms, structured outputs).

Problem 3: You need discovery

If an agent is going to delegate, it must discover capabilities: “Who can do inventory checks?” “Who can approve spending?” “What modalities do they accept?”

Problem 4: Enterprises need governance

Identity, authentication, authorization, audit logs, versioning, and safe handling of files/URLs must be aligned with typical enterprise security practices.

A2A is not “a prompt format.” It’s a collaboration protocol with discovery, structured data, and lifecycle.

3) Core concepts and vocabulary

These are the A2A building blocks you should hold in your head:

Concept Meaning Why it matters
Agent A network service that can accept tasks and return results. Agents are peers: each can delegate to another agent.
AgentCard A machine-readable “business card” that describes an agent's interfaces, skills, modalities, capabilities, and security requirements. Enables discovery and safe routing.
Skill A declared capability like “check_inventory” or “approve_purchase”. Used to choose the right agent for a subtask.
Task The core unit of delegated work with an id, contextId, status, optional history, and artifacts. Supports long-running work and human-in-the-loop.
Message A communication unit inside a task (request, update, clarification, final answer). Multi-turn interactions without leaking internal state.
Part A piece of message or artifact content containing exactly one of text, raw bytes, a URL, or structured data. Enables multi-modality and structured payloads.
Artifact An output object produced by the task (report, file, decision record, structured JSON). Separates “conversation” from “deliverables.”
Think “project management”: a Task has a status, Messages are the discussion, and Artifacts are the deliverables. A contextId can group multiple related tasks into one continuing interaction.

4) Agent discovery via AgentCard

Discovery starts with the Agent Card: a JSON document published by an A2A server at a well-known path such as /.well-known/agent-card.json. The purpose is to make it possible for other agents (or an orchestrator) to learn:

  • Who this agent is (name/version/vendor)
  • Where to send requests and which bindings/versions each endpoint supports
  • What the agent can do (skills)
  • How to authenticate (schemes, requirements)
  • What interaction styles it supports (streaming, push notifications, extended card)
Concierge agent wants “inventory check” ↓ GET well-known AgentCard for candidate agents ↓ Choose agent whose Skills match the needed work ↓ Create Task + exchange Messages/Artifacts until complete
Security note: even though the AgentCard is a discovery document, you should treat it as a potentially sensitive surface and protect it appropriately (don’t embed secrets).

4.1 Interface selection is ordered, not guessed

A 1.0 Agent Card can list several supportedInterfaces in preference order. A client chooses the first binding it supports and uses that interface's URL and protocol version. If the interface declares an opaque tenant routing value, the client copies it into every request for that interface.

BindingBest fitStreaming
HTTP+JSONREST-oriented services and browser-friendly infrastructureServer-Sent Events
JSONRPCRPC-oriented clients over HTTPServer-Sent Events
GRPCStrongly typed internal platforms and generated clientsgRPC server streaming

Public cards must not contain credentials. When capabilities.extendedAgentCard is enabled, an authenticated client can fetch a richer card after obtaining credentials out of band. Cards may also be signed with JWS after JSON Canonicalization Scheme normalization when provenance and tamper detection are required.

5) Skills: how agents advertise capability

A2A “Skills” are intentionally high-level: they describe what an agent does in a way another system can reason about. Skills are not the internal tool list, not chain-of-thought, and not implementation details.

A skill typically answers:
  • What the agent can do (“approve_purchase”, “inventory_availability”)
  • Input modes and examples that help a router understand when the skill applies
  • Output modes returned through artifacts
  • Constraints (needs human approval, requires certain auth scope)

Practically, your orchestrator (concierge) uses skills like a routing index: “Which agent should I hire for this sub-problem?”

6) Tasks, status, and long-running work

A2A is “async-first.” That means it is designed for tasks that may take time: waiting on a human, waiting on another system, or doing multi-step reasoning.

A2A 1.0 task states:
StateMeaningTerminal?
TASK_STATE_UNSPECIFIEDUnknown or indeterminate state; avoid creating tasks in this state.No
TASK_STATE_SUBMITTEDAccepted and acknowledged.No
TASK_STATE_WORKINGActively being processed.No
TASK_STATE_INPUT_REQUIREDMore user input is required.Interrupted
TASK_STATE_AUTH_REQUIREDAuthorization must be fulfilled through an agreed mechanism.Interrupted
TASK_STATE_COMPLETEDFinished successfully; inspect artifacts for deliverables.Yes
TASK_STATE_FAILEDFinished with an error.Yes
TASK_STATE_CANCELEDCanceled before completion.Yes
TASK_STATE_REJECTEDThe agent decided not to perform the task.Yes

Earlier diagrams often called these states created, running, needs input, blocked, and succeeded. Those remain useful plain-English descriptions, but they are not the 1.0 wire values. External-system waiting is normally represented as TASK_STATE_WORKING plus a status message; user clarification and authorization have their own explicit states.

Why tasks exist: If agents only did one-shot request/response, they’d fail on most real workflows. Tasks let agents coordinate across time, state, and dependencies.

7) Messages, parts, and artifacts

7.1 Messages

A Message is “what we said” within an interaction: a request, clarification, follow-up, or status explanation. Every Message has a creator-assigned messageId, a role, and at least one Part. The two wire roles are ROLE_USER for client-to-agent messages and ROLE_AGENT for agent-to-client messages. contextId and taskId associate later turns with ongoing work.

7.2 Parts

A Part is “what kind of content this is.” A2A is modality-agnostic. A Part contains exactly one of text, base64-encoded raw bytes, a file url, or JSON-compatible data. File metadata such as filename and media type sits beside the chosen content field.

7.3 Artifacts

Artifacts are the outputs: a report, a decision, a JSON payload, an attached file reference, a filled form. Every artifact has an artifactId unique within its task and one or more Parts. The key design win is: artifacts represent deliverables; messages represent conversation.

If you mix “final deliverables” and “chatty conversation” into one blob of text, you make downstream automation fragile. Artifacts fix that by making outputs explicit.
Reliability boundary A task history is not guaranteed to retain every transient Message, and a disconnected stream may miss informational updates. Put durable results in Artifacts and recover current state with task operations; do not use chat messages as a guaranteed event log.

8) Interaction models: sync vs streaming vs async

A2A supports multiple interaction modes so agents can choose what is appropriate:

Mode When to use How it feels
Synchronous Fast tasks that can complete quickly. SendMessage returns a direct Message or a completed Task.
Streaming You want progress updates or partial results. SendStreamingMessage emits the initial Task or Message, then status/artifact update events.
Asynchronous Long-running tasks, human-in-loop approvals, external dependencies. Receive a submitted/working Task, then poll, subscribe, or configure authenticated push notifications.
A2A is built to treat “waiting” as normal. That’s why the task object and its status/history are central.

The binding changes the transport shape, not the meaning. For example, HTTP+JSON uses POST /message:send, JSON-RPC invokes SendMessage, and gRPC calls the generated SendMessage method. All three carry the same canonical request and produce functionally equivalent objects.

9) Orchestration patterns

In multi-agent systems, there are common architectures:

Concierge (Orchestrator) Pattern

One “front” agent speaks to the user and hires specialist agents for subtasks. This keeps the user experience consistent and concentrates policy + governance in one place.

User ↔ Concierge ↙ ↘ Inventory Approval
Hub-and-Spoke (Platform) Pattern

A central platform routes tasks and enforces org-wide authentication, authorization, quotas, and auditing. Individual agents remain independent services.

Agents ↔ Hub ↔ Agents
Mesh (Peer-to-Peer) Pattern

Agents directly discover and delegate to each other. Powerful, but harder to govern unless you add strong identity and allow-lists.

Agent A ↔ Agent B ↔ Agent C ↖──────────↙
Human-in-the-Loop Variant

One or more tasks become “blocked” until a human approves or provides missing information. A2A’s async-first model makes this a first-class concept.

If you’re building your first system, start with the concierge pattern. It’s easiest to debug, easiest to secure, and easiest to explain.

10) Concrete scenario: Purchasing Concierge + Inventory + Approval

Let’s implement the exact “why do we need this and what does it do?” story using A2A. Your user says: “Buy 20 keyboards for the team.” The concierge agent must:

  1. Find an inventory agent to check stock and pricing
  2. Find an approval agent to approve budget (human-in-loop)
  3. Return a final “approved purchase plan” to the user
Agents (roles)
  • Concierge Agent: user-facing, orchestrates subtasks
  • Inventory Agent: checks availability, lead time, estimated cost
  • Approval Agent: determines if purchase is allowed and records approval

10.1 Step-by-step flow (exactly what happens)

  1. Discovery: Concierge fetches AgentCards for Inventory and Approval agents.
  2. Routing: Concierge selects agents by matching required Skills.
  3. Delegate inventory task: Concierge creates a Task on Inventory agent: “Check 20 keyboards.”
  4. Inventory responds: Inventory produces an Artifact: availability + cost breakdown.
  5. Delegate approval task: Concierge creates a Task on Approval agent with the cost breakdown.
  6. Approval pauses: Approval agent returns TASK_STATE_INPUT_REQUIRED with a Message explaining which manager decision is needed.
  7. Human approves: Concierge (or UI) submits approval decision back to Approval agent.
  8. Approval completes: Approval agent transitions to TASK_STATE_COMPLETED and emits an approval Artifact (decision + approver + timestamp).
  9. Concierge finalizes: Concierge returns a final plan to the user.
This is what A2A “gives you”: the structured way to discover agents, start tasks, wait safely, and collect artifacts. Without a shared protocol, each integration must invent discovery, payloads, status semantics, versioning, and long-running state.

Notice the separation: a status Message explains what the interaction needs next, while the final approval decision belongs in an explicit Artifact that downstream systems can validate and audit.

12) Security and authorization boundaries

A2A intentionally relies on standard web security practices. That means:

Transport security
  • Use HTTPS for integrity and authenticity
  • Verify the server certificate; consider mTLS between workloads
Authentication
  • Bearer tokens obtained through OAuth/OIDC are common
  • Service-to-service credentials for private deployments
Authorization
  • Scopes/roles per skill (for example, approval:write)
  • Don’t let “any agent” call “any skill”
File/URL safety
  • Validate file references to avoid SSRF
  • Sanitize and validate user-provided data parts
Practical governance recommendation: Use allow-lists for which agents your concierge is permitted to hire, and limit which skills can be invoked based on policy.

12.1 Discovery describes security; it does not issue credentials

securitySchemes describes supported mechanisms and securityRequirements states which are required. The client obtains credentials through the appropriate out-of-band OAuth, workload, API-key, or certificate flow and transmits them through binding-specific headers or metadata on every request. The agent authenticates and authorizes each request; an Agent Card entry is not an access grant.

12.2 Authentication during a task is a state, not a credential envelope

If later work needs additional authorization, the agent may transition the Task to TASK_STATE_AUTH_REQUIRED and explain the requirement in its status Message. Credentials remain out of ordinary Messages and Artifacts unless a separately negotiated extension defines a protected in-band mechanism.

12.3 Push callbacks form a second trust boundary

A push notification endpoint is an inbound API. Use a high-entropy callback URL or authenticated webhook token, validate the expected Task ID, reject unknown senders, apply replay/idempotency controls, and return a 2xx response only after durable acceptance. Delivery may be duplicated, so handlers must be idempotent.

13) Mechanics-first Python simulator (server + concierge client)

Below is the original minimal educational implementation, retained because writing the storage and routing mechanics by hand makes the lifecycle concrete. It publishes a card, accepts delegated work, tracks status, and returns an artifact.

Boundary of the example This FastAPI service is an A2A-shaped simulator, not a compliant A2A 1.0 server: it uses the private endpoint POST /a2a/tasks and omits binding-level version negotiation, streaming events, formal error mappings, and several required fields. Use an official or maintained A2A SDK for interoperability. The simulator exists to expose the moving parts before the SDK hides them.

13.1 Specialist agent lifecycle simulator (FastAPI)

# inventory_agent.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import uuid, time

app = FastAPI(title="Inventory Agent (A2A demo)")

# In-memory task store (demo only)
TASKS = {}

def agent_card():
    return {
        "name": "Inventory Agent",
        "description": "Checks stock, price, and ETA for purchase requests.",
        "supportedInterfaces": [{
            "url": "http://127.0.0.1:9101/a2a",
            "protocolBinding": "HTTP+JSON",
            "protocolVersion": "1.0",
        }],
        "version": "1.0.0",
        "capabilities": {
            "streaming": False,
            "pushNotifications": False,
        },
        "defaultInputModes": ["text/plain", "application/json"],
        "defaultOutputModes": ["application/json"],
        "skills": [
            {
                "id": "inventory.check",
                "name": "Inventory Check",
                "description": "Returns stock, price, ETA, and estimated total.",
                "tags": ["inventory", "pricing", "procurement"],
                "examples": ["Check availability for 20 keyboards."],
            }
        ]
    }

# Well-known discovery document (demo path)
@app.get("/.well-known/agent-card.json")
def get_agent_card():
    return agent_card()

class CreateTask(BaseModel):
    skillId: str
    message: dict

@app.post("/a2a/tasks")
def create_task(body: CreateTask):
    if body.skillId != "inventory.check":
        raise HTTPException(status_code=400, detail="Unsupported skillId")

    task_id = f"task_{uuid.uuid4().hex[:8]}"

    # Parse the structured data part if present
    item = "unknown"
    qty = 1
    for part in body.message.get("parts", []):
        if "data" in part:
            data = part.get("data", {})
            item = data.get("item", item)
            qty = data.get("quantity", qty)

    # Demo logic
    available = 18 if item.lower() == "keyboard" else 5
    unit_price = 35.0 if item.lower() == "keyboard" else 10.0
    eta_days = 7 if qty > available else 0
    total = float(qty) * unit_price

    TASKS[task_id] = {
        "id": task_id,
        "contextId": "demo-purchase",
        "createdAt": time.time(),
        "status": {"state": "TASK_STATE_COMPLETED"},
        "artifacts": [{
            "artifactId": f"artifact_{uuid.uuid4().hex[:8]}",
            "name": "Inventory quote",
            "parts": [{
                "data": {
                    "item": item,
                    "quantity": qty,
                    "available": available,
                    "backorderEtaDays": eta_days,
                    "unitPrice": unit_price,
                    "currency": "USD",
                    "estimatedTotal": total,
                }
            }]
        }]
    }

    return TASKS[task_id]

@app.get("/a2a/tasks/{task_id}")
def get_task(task_id: str):
    t = TASKS.get(task_id)
    if not t:
        raise HTTPException(status_code=404, detail="Unknown task")
    return t

13.2 Concierge client: discover skills, create a task, read artifact

# concierge.py
import uuid
import requests

INVENTORY_BASE = "http://127.0.0.1:9101"

def discover_agent(base: str) -> dict:
    r = requests.get(base + "/.well-known/agent-card.json", timeout=5)
    r.raise_for_status()
    return r.json()

def create_inventory_task(base: str, item: str, qty: int) -> dict:
    payload = {
      "skillId": "inventory.check",
      "message": {
        "role": "ROLE_USER",
        "messageId": f"msg_{uuid.uuid4().hex[:8]}",
        "parts": [
          {"text": f"Check availability and pricing for {qty} {item}s."},
          {"data": {"item": item, "quantity": qty}}
        ]
      }
    }
    r = requests.post(base + "/a2a/tasks", json=payload, timeout=10)
    r.raise_for_status()
    return r.json()

if __name__ == "__main__":
    card = discover_agent(INVENTORY_BASE)
    print("Discovered agent:", card["name"], "skills=", [s["id"] for s in card["skills"]])

    task = create_inventory_task(INVENTORY_BASE, "keyboard", 20)
    print("Task status:", task["status"]["state"])
    artifact = task["artifacts"][0]["parts"][0]["data"]
    print("Quote artifact:", artifact)
Even in this simplified demo, you can see the A2A “shape”: discover an agent (AgentCard), pick a skill, create a task, receive an artifact. The next implementation increment is to add the approval agent and model TASK_STATE_INPUT_REQUIRED before completion.

14) Operational checklist (retries, idempotency, observability)

Idempotency
  • Task creation should be safe to retry (idempotency keys)
  • Artifact writes should be append-only or versioned
  • Use unique Message IDs and deduplicate webhook deliveries
Retries + timeouts
  • Use bounded retries with jitter
  • Different timeouts for: card fetch, create task, poll task
  • Do not retry a non-idempotent operation without a stable key
Observability
  • Trace IDs per task and propagate them across agents
  • Log skill invoked, caller identity, status transitions
  • Correlate contextId, taskId, and messageId
Safety
  • Validate file references and URLs (SSRF defense)
  • Keep AgentCards free of secrets
  • Use allow-lists for which agents can be contacted
  • Honor A2A-Version; reject unsupported versions explicitly
The easiest multi-agent failures are “silent failure” and “infinite waiting.” Always implement: (1) clear status transitions, (2) timeouts, (3) explicit failure artifacts.

14.1 Concurrency and terminal-state rules

Treat the Task store as a concurrent state machine. Use compare-and-set or a transactional version column so two workers cannot both advance the same Task from WORKING to conflicting outcomes. A terminal Task must not return to a non-terminal state. Cancellation is a request to stop: workers still need cooperative checks and resource cleanup.

14.2 Cache discovery, not authorization decisions

Agent Cards change relatively slowly and should use normal HTTP caching with Cache-Control, ETag, and conditional requests. Cache the card, but authenticate and authorize each task operation independently. A cached declaration that a skill exists does not prove the current caller may invoke it.

Summary: the complete mental model

  • AgentCard enables discovery: who the agent is, what it can do, how to call it.
  • Skills enable routing: choose the right specialist agent for a subtask.
  • Tasks enable long-running collaboration: statuses, multi-turn messages, and deliverable artifacts.
  • Messages/Parts enable structured, multi-modality communication.
  • Artifacts are explicit outputs that downstream automation can reliably consume.
  • Bindings change transport syntax, while the canonical Task/Message/Artifact model stays equivalent.
  • Version and security are explicit on the boundary; agent autonomy does not bypass enterprise controls.
