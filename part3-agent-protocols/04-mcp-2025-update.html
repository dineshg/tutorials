MCP Protocol Evolution: 2025 Foundations to the 2026 Stateless Core

The earlier chapters establish MCP's durable mental model: a host contains clients, clients connect to servers, and servers expose tools, resources, and prompts. This chapter adds the version dimension. MCP changed substantially during 2025 and again in the 2026-07-28 specification. The capability model remains recognizable, but connection state, discovery, subscriptions, server requests, tasks, and registration changed.

Read the version before copying a wire example. The 2025 session-based protocol and the 2026 stateless protocol are both explained because existing systems may still implement either one. A production client should negotiate or explicitly select the protocol version; it should never combine fields from the two eras.

1) What stays stable across versions

MCP standardizes how an AI application discovers and invokes external capabilities. All versions in this chapter use JSON-RPC 2.0 messages and preserve three server-facing primitives:

PrimitivePurposeTypical example
Tool Perform an operation with typed arguments. orders/create or weather/get
Resource Expose addressable context that can be read on demand. doc://contracts/acme-msa
Prompt Publish a reusable, parameterized message template or workflow. A code-review or incident-triage prompt

The host still owns the trust decision. A tool description is not proof that the tool is safe; the host must authenticate the server, constrain what can be called, validate arguments, obtain appropriate user consent, and render results as untrusted content.

2) The two protocol eras

Concern2025 protocol family2026-07-28 core
Context Negotiated during initialize; optionally tied to Mcp-Session-Id. Every request is self-contained; protocol version and capabilities travel in _meta.
Discovery Initialization and feature-specific list calls. server/discover advertises versions, capabilities, and server identity.
Server notifications A transport-level GET stream and resource subscribe/unsubscribe calls. subscriptions/listen is an explicit long-lived request.
More client input Server-initiated requests such as elicitation/create. An input_required result asks the client to retry with input responses.
Long-running tasks Introduced experimentally in the core. Moved to the official io.modelcontextprotocol/tasks extension.
Compatibility rule The 2025 sections below are not disposable history. They explain why Streamable HTTP, protected-resource metadata, structured output, and resource links exist. When implementing, however, use the message shapes for the version your client and server actually select.

3) The current stateless request model

3.1 Discovery replaces the mandatory handshake

In the current protocol, a server must implement server/discover. A client may call it before other methods to choose a supported version and inspect capabilities, or it may optimistically send another request and handle an unsupported-version error. 

{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "book-example-host",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

A successful result includes resultType: "complete", supported protocol versions, server capabilities, server identity metadata, and cache hints. Discovery is useful for up-front negotiation, but it does not create a session.

3.2 Every request carries its own protocol context

{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "quote",
    "arguments": {"symbol": "ACME"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "book-example-host",
        "version": "1.0.0"
      }
    }
  }
}

The server must be able to process this request without remembering an earlier initialize call, connection, conversation, or process. If an application needs state across calls, the server returns an explicit identifier, such as task_7f12 or checkout_session_91, and the client passes that handle in later arguments.

Why statelessness matters Any healthy instance can process the next request. Load balancers no longer need sticky sessions, a reconnect does not erase hidden protocol state, and task or conversation identity is visible in application data rather than inferred from a socket.

3.3 Result types make continuation explicit

Every current result has a resultType. Ordinary final responses use "complete". A response that needs more information uses "input_required". Clients talking to an older server treat a missing resultType as "complete" for backward compatibility.

4) Transport evolution: HTTP+SSE to Streamable HTTP

4.1 Before Streamable HTTP

Early remote MCP examples exposed two coordinated endpoints: POST /messages carried client-to-server requests and GET /sse held a Server-Sent Events channel for server-to-client messages. Deployments had to coordinate two endpoints, preserve connection affinity, and survive load-balancer idle timeouts.

4.2 The 2025 Streamable HTTP model

The 2025-03-26 family introduced one endpoint, commonly /mcp:

  • POST /mcp accepted a JSON-RPC request and returned either one JSON response or an SSE response stream containing the result and request-scoped progress.
  • GET /mcp could open an independent SSE stream for notifications such as resource changes, sampling, or elicitation.
  • The initialize response could issue Mcp-Session-Id, and later requests sent the negotiated MCP-Protocol-Version.

This was a major improvement over the two-endpoint HTTP+SSE transport, and many deployed clients still use it. It is also the context in which calls such as mcp.run(transport="streamable-http") first appeared in SDK examples.

4.3 The 2026 Streamable HTTP model

Streamable HTTP remains, but the protocol-level session and GET notification stream do not. The current model uses:

  • self-contained POST requests with required protocol metadata;
  • the Mcp-Method and Mcp-Name request headers for HTTP routing consistency;
  • request-scoped response streams for progress and log notifications;
  • subscriptions/listen when a client explicitly wants selected change notifications;
  • a new request ID when retrying after a broken in-flight response stream.
HTTP boundary security Validate the Origin header to defend against DNS rebinding, bind local-only servers to loopback, require HTTPS and authentication for remote servers, and never treat CORS as authorization.

5) Authorization: protected resources and least privilege

A simple bearer-token middleware is useful for learning. Production remote MCP uses the protocol's OAuth profile and the same resource-server principles developed in Part II:

  1. The MCP server is the protected resource. Its /.well-known/oauth-protected-resource metadata identifies trusted authorization servers.
  2. Public clients use Authorization Code with PKCE. OAuth 2.1 remains an Internet-Draft, so treat "OAuth 2.1" as a modern profile: follow the current OAuth security best practices and avoid implicit and password grants.
  3. The client includes a resource indicator so the access token is minted for this MCP resource rather than silently replayed at another server.
  4. The server validates JWTs with issuer metadata and JWKS, or validates opaque tokens through introspection. It checks issuer, audience/resource, expiry, and required scopes.
  5. Authorization-server issuer binding matters: credentials issued by one authorization server must not be reused at another.

The 2025 guidance used Dynamic Client Registration (RFC 7591) for clients unknown to the authorization server. In the current specification it is deprecated in favor of Client ID Metadata Documents, although DCR remains a compatibility path for authorization servers that do not yet support the replacement.

End-user versus workload identity DPoP can sender-constrain a public-client token; mTLS is common between workloads; token exchange is the cleanest way for a host to obtain a downstream token that represents an authorized user delegation. Do not forward an upstream access token merely because both services accept JWTs.

6) From elicitation to multi-round-trip requests

6.1 The 2025 elicitation model

A tool sometimes needs a missing parameter, clarification, or confirmation. The 2025 protocol introduced elicitation/create, a server-initiated request routed through the host to the user: 

# Historical 2025-style conceptual FastMCP API
@mcp.tool()
async def book_flight(ctx, origin: str, destination: str) -> dict:
    if not origin:
        response = await ctx.elicit(
            message="Which city should I book the flight from?",
            schema={
                "type": "object",
                "properties": {"origin": {"type": "string"}},
                "required": ["origin"],
            },
        )
        if response.action != "accept":
            return {"error": "user_declined"}
        origin = response.content["origin"]
    return await reserve(origin, destination)

The host displayed the prompt, validated the structured response, and returned an accept, decline, or cancel outcome. This established a clean human-in-the-loop contract for sensitive tools.

6.2 The 2026 MRTR model

The current protocol removes server-initiated requests from the core transport. Instead, the server returns an InputRequiredResult. Its inputRequests describe the required elicitation, sampling, or roots input. The client gathers the information and retries the original method with inputResponses. 

{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "resultType": "input_required",
    "inputRequests": [
      {
        "requestId": "origin-city",
        "type": "elicitation",
        "message": "Which city should I book the flight from?"
      }
    ]
  }
}

The exact schema should come from the selected SDK and protocol version. The important mental shift is that the server does not call backward over an assumed session: it returns a continuation requirement, and the client explicitly resumes the operation.

7) Structured tool output

Plain text is useful for a human, but fragile for application code. Structured output lets a tool declare a JSON Schema and return machine-ready data in structuredContent, optionally alongside a readable content rendering: 

@mcp.tool(
    output_schema={
        "type": "object",
        "properties": {
            "price": {"type": "number"},
            "currency": {"type": "string"},
        },
        "required": ["price", "currency"],
        "additionalProperties": False,
    },
)
def quote(symbol: str) -> dict:
    return {"price": 142.55, "currency": "USD"}

The host can render the result as a chart, badge, form, or JSON view without asking the language model to re-parse prose. Current MCP accepts JSON Schema 2020-12 by default and permits a full JSON value in structuredContent. Validators should bound schema depth and composition complexity, and they must not automatically fetch arbitrary network $ref targets.

8) Resource links keep large data out of the immediate context

A search result, PDF, or table dump can consume the model's context before the model knows whether it is relevant. A tool can return a typed resource link instead: 

{
  "content": [
    {
      "type": "text",
      "text": "I found three matching contracts."
    },
    {
      "type": "resource_link",
      "uri": "doc://contracts/2024-Q4/acme-msa.pdf",
      "mimeType": "application/pdf",
      "name": "Acme MSA (2024-Q4)"
    }
  ]
}

The model receives a compact handle. The host can fetch the referenced resource with resources/read only when needed and only after applying authorization and size limits. A URI is a reference, not evidence that the target is safe: defend against SSRF, disallowed schemes, oversized content, and cross-tenant access.

9) Operational changes worth remembering

FeatureCurrent guidanceReason
JSON-RPC batching Use one request per call; batching was removed in 2025-06-18. Clear request lifecycle and streaming semantics.
Progress Keep request-scoped progress on that request's response stream. Avoid cross-request ambiguity.
Change notifications Use subscriptions/listen and opt into specific notification types. Subscriptions become explicit request state.
Tasks Use the official tasks extension, with tasks/get polling and tasks/update for later input. Durable work evolves independently of the core.
Roots, sampling, logging Existing implementations may support them, but new implementations should follow the documented migration paths because these features are deprecated. Reduce connection-coupled client features.
Tool annotations Treat read-only, destructive, idempotent, and open-world hints as untrusted metadata. The host still enforces policy and consent.
Caching Honor ttlMs and cacheScope on cacheable list/read results. Reduce polling without leaking private results through shared caches.
Tracing Propagate traceparent, tracestate, and baggage in _meta. Trace one operation across host, server, and downstream systems.
